1. CONTEXTO Y JUSTIFICACIÓN DE v16
================================================================================

La sesión v16 diseña el dashboard de seguridad operativa (Fase 2.2) y
establece la arquitectura genérica de activos que permite a CERO escalar
de vehículos a cualquier tipo de equipo inspeccionable (escaleras,
taladros, arnés, EPP) sin rehacer código ni base de datos.

Decisiones estratégicas clave:
- El dashboard es la carta de presentación de CERO para vender
- Seguridad vial como protagonista, impacto financiero como susurro
- Tendencias y análisis profundo van a Power BI, no al panel web
- Tablas genéricas desde ahora para no rehacer después
- Fase 1 completamente intacta — no se toca nada que funcione

================================================================================
4. PESTAÑA GENERAL — VISTA GERENCIAL
================================================================================

4.1 Índice de Seguridad Operativa (hero)

Score único de 0 a 100, tipo credit score, mostrado como donut
grande con número central. Incorpora todos los activos y permisos
activos en el sistema.

Fórmula parametrizable por empresa. Variables:
- % cumplimiento de inspecciones
- Cantidad de bloqueos resueltos vs pendientes
- Documentos al día vs vencidos
- Novedades críticas abiertas
- Tiempo de respuesta del supervisor

Cuando se implemente Fase 3, el índice incorpora automáticamente
equipos y permisos sin cambiar la estructura.

Muestra: score actual + diferencia vs mes anterior + incidentes
prevenidos.

4.2 KPIs de seguridad (fila principal)

4 tarjetas:
- Riesgos prevenidos — bloqueos detectados antes de operar
- Cumplimiento inspecciones — % con delta vs mes anterior
- Activos operativos — X de Y, con fuera de servicio
- Documentación al día — % con alerta de por vencer

4.3 KPIs financieros (el susurro)

3 tarjetas con tipografía más discreta que los KPIs de seguridad:
- Ahorro estimado este mes — multas + paradas evitadas
- Costo diario sin inspeccionar — cuadrilla + sanción
- Sanciones prevenidas — documentos bloqueados a tiempo

Valores parametrizables por empresa en configuracion_sede:
- costo_dia_vehiculo_parado
- costo_multa_soat
- costo_multa_tecnomecanica

4.4 Situaciones que requieren atención

Anomalías de patrón en lenguaje gerencial, SIN placas ni seriales:
- Reincidencia: "Falla recurrente en sistema de frenos — 1 vehículo
  con la misma novedad 3 veces en 60 días"
- Patrón: "Desgaste acelerado de llantas — 1 vehículo con 5 reportes
  en 3 meses"
- Anomalía: "Equipo con tiempo excesivo fuera de servicio — 1 vehículo
  lleva 18 días, promedio es 4"

Se calculan cruzando preoperacionales + historial_estado_activo.

4.5 Decisiones del supervisor

3 tarjetas: Autorizadas / A taller / Pendientes
Pendientes muestra tiempo sin respuesta.

4.6 Actividad reciente

Timeline vertical con los últimos eventos, SIN placas:
- "Inspección completada sin novedades — Camioneta estacas"
- "Novedad crítica — sistema de frenos — BLOQUEO"
- "Supervisor autorizó con justificación — Respuesta en 6 min"
- "Tanqueo registrado — 45 litros"

5. PESTAÑA ACTIVOS — VISTA OPERATIVA
================================================================================

5.1 Filtro por tipo de activo

Barra de pills horizontal:
Todos | Vehículos | Escaleras | Taladros | Arnés / EPP

Los tipos sin datos aparecen en gris (opacity 0.4).
Cuando se implemente Fase 3, se activan automáticamente.

5.2 KPIs operativos

4 tarjetas:
- Inspecciones esta semana (con delta)
- Con novedades (% del total)
- Bloqueos generados (con estado)
- Promedio días fuera de servicio

5.3 Gráfico: Novedades vs decisión del supervisor

Barras apiladas por mes (6 meses):
- Rojo: Bloqueos
- Azul: Enviados a taller
- Verde: Autorizados

Muestra la relación entre lo que se detecta y lo que se decide.
Si la mayoría se autoriza, puede indicar tolerancia excesiva.
Si la mayoría va a taller, indica flota en mal estado.

5.4 Ítems con más novedades

Barras horizontales con color por severidad:
- Rojo: ítems que generan bloqueo
- Naranja: ítems que generan alerta
- Azul: ítems informativos

5.5 Activos que requieren atención

Lista con identificación (placas, seriales) — esta vista es para
el administrador que SÍ sabe qué activo es cada uno.
Badge de días en taller + documentos por vencer.

5.6 Reincidencia

Misma novedad reportada 2+ veces en 90 días por activo.
Con placa/serial, descripción de la novedad, frecuencia y última
fecha.

8. BASE DE DATOS — TABLAS GENÉRICAS NUEVAS
================================================================================

Decisión: Camino B — tablas separadas con patrón común.
Fase 1 completamente intacta. No se tocan preoperacionales,
posoperacionales, tanqueos, autorizaciones ni sesiones_activas.

8.1 Tabla tipos_activo

CREATE TABLE tipos_activo (
  id              uuid DEFAULT gen_random_uuid() PRIMARY KEY,
  codigo          text NOT NULL UNIQUE,
  nombre          text NOT NULL,
  categoria       text NOT NULL,
  requiere_inspeccion boolean DEFAULT true,
  frecuencia_inspeccion text DEFAULT 'diaria',
  activo          boolean DEFAULT true
);

Valores iniciales:
- vehiculo / Vehículo / flota / true / diaria
- escalera / Escalera / equipo / true / por_uso
- taladro / Taladro / equipo / true / por_uso
- arnes / Arnés / epp / true / por_uso
- epp / EPP / epp / true / diaria

Campos:
- codigo: identificador único ('vehiculo', 'escalera', etc.)
- categoria: agrupación ('flota', 'equipo', 'epp')
- frecuencia_inspeccion: 'diaria', 'semanal', 'mensual', 'por_uso'

8.2 Tabla activos

CREATE TABLE activos (
  id              uuid DEFAULT gen_random_uuid() PRIMARY KEY,
  tipo_activo_id  uuid NOT NULL REFERENCES tipos_activo(id),
  empresa_id      uuid NOT NULL REFERENCES empresas(id),
  sede_id         uuid REFERENCES sedes(id),
  codigo          text NOT NULL UNIQUE,
  nombre          text NOT NULL,
  estado          text DEFAULT 'operativo',
  datos           jsonb DEFAULT '{}',
  documentos      jsonb DEFAULT '{}',
  activo          boolean DEFAULT true,
  created_at      timestamptz DEFAULT now()
);

CREATE INDEX idx_activos_tipo ON activos(tipo_activo_id);
CREATE INDEX idx_activos_empresa ON activos(empresa_id);
CREATE INDEX idx_activos_sede ON activos(sede_id);
CREATE INDEX idx_activos_estado ON activos(estado);

Campos:
- codigo: placa (vehículos), serial (escaleras), código interno
- nombre: descripción legible ('Toyota Hilux MSO120', 'Escalera #14')
- estado: 'operativo', 'taller', 'retirado', 'bloqueado'
- datos: JSONB con datos específicos del tipo (marca, modelo, año,
  capacidad, material, largo, etc.)
- documentos: JSONB con fechas de vencimiento aplicables

Vinculación con vehículos existentes:
- Se agrega campo activo_id (uuid FK) a tabla vehiculos
- Cada vehículo existente se vincula a un registro en activos
- Los flujos de WhatsApp siguen usando la tabla vehiculos
- El dashboard consulta activos para la vista unificada

8.3 Tabla historial_estado_activo

CREATE TABLE historial_estado_activo (
  id              uuid DEFAULT gen_random_uuid() PRIMARY KEY,
  activo_id       uuid NOT NULL REFERENCES activos(id),
  estado_anterior text,
  estado_nuevo    text NOT NULL,
  motivo          text,
  categoria_motivo text,
  referencia_id   uuid,
  referencia_tipo text,
  cambiado_por    uuid,
  sede_id         uuid REFERENCES sedes(id),
  timestamp       timestamptz DEFAULT now()
);

CREATE INDEX idx_historial_activo ON historial_estado_activo(activo_id);
CREATE INDEX idx_historial_timestamp ON historial_estado_activo(timestamp DESC);
CREATE INDEX idx_historial_estado ON historial_estado_activo(estado_nuevo);

Campos:
- categoria_motivo: 'documento', 'novedad_bloqueo', 'mantenimiento',
  'retirado', 'manual'
- referencia_id: UUID del preoperacional, autorización, etc.
- referencia_tipo: 'preoperacional', 'autorizacion', 'alerta', 'manual'
- cambiado_por: UUID de conductor o usuario_panel

Con esta tabla se calcula:
- Días en cada estado por activo
- Frecuencia de motivos de parada
- Reincidencia por activo (mismo motivo N veces en X días)
- Tiempo promedio fuera de servicio
- Anomalías (activo con más días que el promedio)

8.4 Tabla permisos_trabajo

CREATE TABLE permisos_trabajo (
  id                    uuid DEFAULT gen_random_uuid() PRIMARY KEY,
  tipo                  text NOT NULL,
  empresa_id            uuid NOT NULL REFERENCES empresas(id),
  sede_id               uuid REFERENCES sedes(id),
  trabajador_id         uuid REFERENCES conductores(id),
  ubicacion             text,
  descripcion_trabajo   text,
  riesgos_identificados jsonb DEFAULT '[]',
  controles             jsonb DEFAULT '[]',
  equipos_requeridos    jsonb DEFAULT '[]',
  estado                text DEFAULT 'borrador',
  firma_trabajador      boolean DEFAULT false,
  firma_supervisor      boolean DEFAULT false,
  firma_sst             boolean DEFAULT false,
  aprobado_por          uuid,
  fecha_inicio          timestamptz,
  fecha_fin             timestamptz,
  observaciones         text,
  pdf_url               text,
  created_at            timestamptz DEFAULT now()
);

CREATE INDEX idx_permisos_tipo ON permisos_trabajo(tipo);
CREATE INDEX idx_permisos_estado ON permisos_trabajo(estado);
CREATE INDEX idx_permisos_sede ON permisos_trabajo(sede_id);

Campos:
- tipo: 'ats', 'altura', 'riesgo_electrico', 'espacio_confinado'
- estado: 'borrador', 'pendiente', 'aprobado', 'rechazado', 'cerrado'
- Tres firmas independientes: trabajador, supervisor, SST
- riesgos_identificados: array de riesgos en JSONB
- controles: medidas de control aplicadas
- equipos_requeridos: EPP, herramientas, equipos

8.5 Cambios en tablas existentes

-----------------------------------------------------------
Tabla              | Campo nuevo   | Tipo    | Notas
-----------------------------------------------------------
vehiculos          | activo_id     | uuid FK | Vincula con
                   |               |         | tabla activos
-----------------------------------------------------------

Estrategia de migración:
1. Crear las 4 tablas nuevas
2. Insertar tipos_activo base (vehiculo, escalera, etc.)
3. Crear un registro en activos por cada vehículo existente
4. Actualizar vehiculos.activo_id con el activo correspondiente
5. Insertar registro inicial en historial_estado_activo por
   cada vehículo (estado actual como punto de partida)

8.6 Claves de configuración nuevas en configuracion_sede

9. PATRÓN PARA FUTURAS INSPECCIONES (FASE 3)
================================================================================

Cuando se implementen inspecciones de escaleras, taladros, arnés,
cada tipo crea su propia tabla siguiendo este patrón:

CREATE TABLE inspecciones_[tipo] (
  id              uuid DEFAULT gen_random_uuid() PRIMARY KEY,
  activo_id       uuid NOT NULL REFERENCES activos(id),
  conductor_id    uuid REFERENCES conductores(id),
  sede_id         uuid REFERENCES sedes(id),
  fecha           timestamptz DEFAULT now(),
  items           jsonb NOT NULL DEFAULT '{}',
  novedades       jsonb DEFAULT '[]',
  estado          text DEFAULT 'en_curso',
  firma_operario  boolean DEFAULT false,
  firma_timestamp timestamptz,
  pdf_url         text,
  created_at      timestamptz DEFAULT now()
);

Campos obligatorios en novedades JSONB:
- item: nombre del ítem
- critico: boolean
- resultado: 'bueno' / 'malo'
- severidad: 'informativo' / 'alerta' / 'bloqueo'
- detalle: texto del sub-pregunta si aplica

El dashboard consulta todas las tablas de inspección con el mismo
formato de novedades, permitiendo KPIs cruzados.
